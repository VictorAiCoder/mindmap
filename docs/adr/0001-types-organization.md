## Контекст

В проекте исторически сложилась папка `src/types/` со множеством типов
разной природы. Файл `mindmap-api.ts` разросся до ~70 строк и стал
"свалкой" контрактов: интерфейсы композиблов, типы layout-движка,
типы экспорта/импорта — всё в одном месте.

Это создавало проблемы:

- **Высокая связность.** Любое изменение API одного композибла требовало
  правки `mindmap-api.ts`, который импортировался десятками файлов.
- **Размытая ответственность.** Непонятно, где должен жить новый тип:
  в `src/types/`, рядом с реализацией, или в `@entities/`?
- **Мёртвый код.** Типы `LayoutFn`, `LayoutPositions` лежали без
  потребителей — обнаружилось это только при миграции.
- **Дубликаты.** `PositionMap` (в `types/layout.ts`) и `LayoutPositions`
  (в `mindmap-api.ts`) описывали одну и ту же структуру.

## Решение

Принят **трёхслойный принцип** организации типов:

### 1. Доменные типы → `@entities/*`

Типы, описывающие **бизнес-сущности** (узлы, позиции, связи), живут
в entity-слое.

```ts
// @entities/node
export interface MindMapNode { ... }
export interface ScenePosition { x: number; y: number }
export interface Center2D { cx: number; cy: number }
```

**Принцип:** entity-типы не зависят от Vue, композиблов или UI.

### 2. Контракты композиблов → рядом с реализацией

Если `useFoo.ts` экспортирует функцию `useFoo()`, то и интерфейс
`FooApi` живёт в **том же файле**.

```ts
// src/composables/tree/useTreeOperations.ts
export interface TreeOperationsApi { ... }
export function useTreeOperations(...): TreeOperationsApi { ... }
```

**Принцип:** контракт и реализация эволюционируют вместе.
Исключения (когда тип выносится в отдельный файл `types.ts` рядом):

- Тип используется **до** объявления функции (циклическая зависимость).
- Группа связанных типов слишком велика для co-location
  (см. `composables/layout/types.ts`).

### 3. Публичный API приложения → тонкий barrel

`src/types/mindmap-api.ts` — **фасад**, не свалка. Содержит:

- Re-export всех публичных контрактов из композиблов.
- Главный композитный интерфейс `MindMapApi` (объединение всех API).

```ts
// src/types/mindmap-api.ts
export type { HistoryApi } from '@/composables/useHistory'
export type { TreeOperationsApi } from '@/composables/tree/useTreeOperations'
// ... остальные re-exports

export interface MindMapApi extends TreeOperationsApi, PersistenceApi, ... {
  rootNode: Ref<MindMapNode>
  // ... корневые поля
}
```

**Кто импортирует через `mindmap-api.ts`?** UI-компоненты
(`App.vue`, `ToolbarPanel.vue`). Им нужен **стабильный фасад**.

**Кто импортирует напрямую?** Композиблы между собой. Им важна
точность зависимостей (без лишних уровней).

### Особый случай: `src/types/layout.ts`

Это **второй валидный barrel** проекта. Содержит публичные контракты
layout-слоя: `LayoutPosition`, `LayoutBounds`, `LayoutData`, `PositionMap`.

Не объединён с `mindmap-api.ts`, потому что:

- Не входит в API верхнего уровня (`useMindMap`).
- Используется множеством internal-консьюмеров (canvas, drag, connections).
- Имеет свою собственную смысловую целостность.

## Последствия

### ✅ Плюсы

- **Локальность изменений.** Меняется API композибла — меняется один файл.
- **Самодокументация.** Структура папок отражает архитектуру.
- **Меньше merge-конфликтов.** Нет файла, в который "все коммитят".
- **Findability.** `Go to definition` ведёт сразу к реализации.

### ⚠️ Минусы / компромиссы

- **Два пути импорта** для одного типа (`from '@/composables/...'`
  vs `from '@/types/mindmap-api'`). Решено правилом:
  **UI → barrel, композиблы → прямой путь.**
- **`src/types/` остаётся**, но в минимальном виде. Альтернатива
  (полное упразднение) была отвергнута: `mindmap-api.ts` и `layout.ts`
  имеют ясное предназначение как фасады.

## Правила для нового кода

### Куда положить новый тип?

```
Это бизнес-сущность? ──→ @entities/<domain>
   │ нет
   ▼
Это контракт композибла? ──→ В тот же файл, что и сам useFoo()
   │ нет
   ▼
Это семейство связанных типов слоя?
   │   (layout, persistence, image…)
   ├─ да ──→ src/composables/<layer>/types.ts
   │
   └─ нет ──→ Скорее всего, ты что-то делаешь не так.
              Перепроверь — возможно, это контракт композибла.
```

### Когда добавлять re-export в `mindmap-api.ts`?

Только если тип **импортируется UI-компонентами**.
Внутренние типы (например, `SegmentOperationsApi` без UI-потребителей)
re-export'ить не нужно.

## 🤔 Критические замечания к ADR

Прежде чем коммитить — **подумай**, не хочешь ли что-то изменить:

### 1. Формат ADR — сокращённый
Я написал в **прагматичном** стиле, не в академическом «Michael Nygard format» (Status / Context / Decision / Consequences с жёсткими заголовками). Если хочешь канонический формат — могу переписать.

### 2. Дата
Замени `2025-XX-XX` на сегодняшнюю.

### 3. «Связанные документы»
Если у тебя есть конвенция именования коммитов или PR — можно сослаться на конкретный коммит/PR.

### 4. Раздел «История миграции»
Это **дополнительный** контекст. Можно убрать, если хочешь, чтобы ADR был чисто про **правила**, а не про **прошлое**. Я оставил, потому что это даёт понимание «откуда мы пришли», что полезно для коллег.

### 5. Спорный момент: формулировка про `src/types/layout.ts`
Я назвал его «вторым валидным barrel». Это **компромисс**: чистый принцип сказал бы «всё в `composables/layout/`». Если ты в будущем захочешь убрать `src/types/` целиком — этот пункт ADR придётся пересматривать. **Я готов отстоять текущую формулировку**, но если ты считаешь, что это оставляет лазейку для будущих свалок — давай переформулируем жёстче.
