# MindMap

Редактор mind map, где источник данных — обычный markdown-файл. Импортируй `.md` — получи интерактивную карту. Редактируй визуально — экспортируй обратно в чистый markdown. Проект построен как мост между структурированным текстом и пространственным мышлением, с поддержкой кода, подсветки синтаксиса и markdown-заметок на каждом узле.

## ✨ Зачем этот проект

Большинство mind map инструментов запирают данные в проприетарных форматах. MindMap построен вокруг markdown как источника истины — и это делает его удобным для:

- **Работы с LLM** — вставь структурированный ответ от ChatGPT/Claude и сразу получи навигируемую карту
- **Базы знаний в Git** — нормальные diff'ы, code review, версионирование
- **Обратимой сериализации** — любое визуальное изменение чисто ложится обратно в markdown, без потерь

## 🎯 Возможности

- 📥 **Двунаправленный markdown I/O** — импорт и экспорт вложенных структур, заметок и блоков кода без потерь
- 🌲 **Шесть стратегий раскладки** — radial, compact, spacious, tree-down, tree-right, mind-map — переключаются на лету
- 📝 **Markdown-заметки на каждом узле** с поддержкой GFM (таблицы, чек-листы, цитаты)
- 🎨 **Подсветка синтаксиса для 50+ языков** через `highlight.js` (тема atom-one-dark)
- 🖼️ **Встроенные изображения** с drag-and-drop
- ↩️ **Полная история undo/redo**
- 🔍 **Плавный pan & zoom** с Bezier-кривыми для связей
- ⚡ **Drag-and-drop редактирование дерева** с визуальными подсказками
- 🌗 **Светлая/тёмная тема** через design-токены Vuetify
- 🛡️ **Защита от XSS** — весь пользовательский markdown санитайзится через DOMPurify

## 🏛️ Архитектурные решения

Этот раздел документирует инженерные принципы, на которых построен код. Раздел намеренно содержательный — за каждым выбором стоит обоснование.

### 1. Composition-first, без state-менеджеров

Ни Pinia, ни Vuex, ни Redux-подобных решений. Всё состояние приложения живёт в **composable-функциях** (`composables/`), каждая из которых отвечает за один слой поведения:

```
useMindMap           → корневой оркестратор
useHistory           → стек undo/redo
useLayout            → диспетчер раскладок
usePersistence       → сохранение/загрузка/импорт/экспорт
usePanZoom           → трансформации вьюпорта
useConnections       → геометрия связей
useNodeDrag          → механика drag
useTreeOperations    → CRUD по дереву
useTreeTraversal     → read-only обход
useNodeFactory       → конструирование узлов
```

Каждый composable идиоматичен для Vue (возвращает реактивные ref'ы, отдаёт типизированный API) и независимо тестируется — см. `useConnections.spec.ts`.

### 2. Strategy Pattern для движков раскладки

Алгоритмы раскладки вынесены в изолированные модули в `composables/layout/`:

```
layoutCompact.ts
layoutMindMap.ts
layoutRadial.ts
layoutSpacious.ts
layoutTreeDown.ts
layoutTreeRight.ts
```

Добавить новую раскладку можно **не трогая ядро** — достаточно положить файл, реализующий контракт `LayoutStrategy`, и зарегистрировать его в `useLayout.ts`. Общая геометрия вынесена в `layoutUtils.ts`, чтобы каждая стратегия оставалась декларативной.

Это применение **Open/Closed Principle** на уровне фич.

### 3. Типобезопасный dependency injection

`provide`/`inject` во Vue мощный, но без типов по умолчанию. В проекте это решено так:

- **`types/injection-keys.ts`** — `InjectionKey<T>` токены для каждого провайдимого контракта
- **`utils/injectStrict.ts`** — обёртка, которая сужает тип и бросает исключение при отсутствии инъекции, убирая `T | undefined` из кода потребителей

```ts
// Код потребителя остаётся чистым и безопасным:
const api = injectStrict(MindMapApiKey)  // Типизировано как MindMapApi, гарантированно non-null
```

### 4. Доменная логика отделена от UI

Модуль `composables/tree/` разделён по принципу SRP:

- **`useNodeFactory.ts`** — создание узлов (Factory)
- **`useTreeOperations.ts`** — мутации: add, remove, move, reparent (Command)
- **`useTreeTraversal.ts`** — чистые read-запросы: find, walk, filter (Visitor)

Компоненты никогда не работают с деревом напрямую. Они вызывают операции; операции записываются в `useHistory`; история проигрывает их в обратном порядке для undo. Таким образом **undo/redo получается бесплатным следствием архитектуры**, а не прикручивается сверху.

### 5. Обратимая markdown-сериализация

`persistence/importMarkdown.ts` и `persistence/exportMarkdown.ts` спроектированы как **обратные функции**: `export(import(md)) ≈ md`. Что это даёт:

- Нет проприетарного формата
- Нет vendor lock-in
- Читаемые diff'ы в Git

### 6. Единая точка рендеринга markdown

`useMarkdown.ts` — **единственное** место, где вызывается `marked.parse`. Все компоненты используют `renderMarkdown(text)` — из чего следует:

- XSS-санитизация применяется **один раз**, на уровне инфраструктуры (через DOMPurify со строгим allow-list)
- Конфигурация подсветки синтаксиса лежит в **одном** месте
- Смена markdown-движка — изменение в одном файле

### 7. Tree-shaken подсветка синтаксиса

Вместо дефолтного бандла `highlight.js` на 1 МБ языки **регистрируются явно** в `composables/notes/hljsSetup.ts`:

- 50 языков выбраны по реальной популярности
- Прописаны распространённые алиасы (`ts` → typescript, `yml` → yaml, `sh` → bash, `html` → xml)
- Размер бандла: **~40 КБ gzip** против ~300 КБ у полной сборки

### 8. Математически корректные UI-примитивы

Связи между узлами рисуются **кубическими кривыми Безье** (`utils/bezier.ts`), с контрольными точками, вычисленными так, чтобы получались естественные органичные линии, а не ломаные. Геометрический модуль **чистый** и покрыт юнит-тестами (`bezier.spec.ts`).

### 9. Темизация через design-токены

Никаких захардкоженных цветов. Все стили используют CSS-переменные Vuetify (`var(--v-theme-surface)`, `rgb(var(--v-theme-primary))`, …). Что это даёт:

- Переключение светлой/тёмной темы — один вызов Vuetify API
- Добавление кастомной темы не требует правки CSS

### 10. Типобезопасность на этапе сборки

`vue-tsc --build` запускается параллельно с билдом Vite (через `npm-run-all2`), что отлавливает ошибки типов и в `.vue` шаблонах, а не только в `.ts` файлах. TypeScript используется как **инструмент корректности**, а не декорация.

## 🧪 Подход к тестированию

Тесты покрывают **чистую доменную логику** — там, где ценность теста на единицу усилий максимальна:

- `utils/bezier.spec.ts` — геометрическая корректность кривых
- `composables/canvas/__tests__/useConnections.spec.ts` — поведение графа связей

UI-компоненты намеренно **не покрываются** юнит-тестами — сам фреймворк (Vue + Vuetify) уже гарантирует корректность рендера, а пользовательские сценарии лучше покрываются E2E-тестами. Это осознанная позиция **test-what-matters**.

Стек: **Vitest** + **happy-dom** + **@vue/test-utils**.

- Node.js `^20.19.0` или `>=22.12.0`


## 📁 Структура проекта

```
src/
├── components/
│   ├── canvas/      # Вьюпорт, zoom, pan, drag-подсказки
│   ├── node/        # Рендеринг узла, actions, контент, превью заметок
│   └── panels/      # Тулбары и редактор заметок
├── composables/
│   ├── canvas/      # Геометрия связей, pan/zoom (+ тесты)
│   ├── drag/        # Drag-and-drop и перетаскивание узлов
│   ├── layout/      # 6 плагинных стратегий раскладки
│   ├── notes/       # Настройка highlight.js
│   ├── persistence/ # Импорт/экспорт markdown
│   ├── tree/        # Factory / operations / traversal дерева
│   └── *.ts         # Cross-cutting: history, theme, markdown, ...
├── types/           # Общие интерфейсы, injection-ключи, API-контракты
└── utils/           # Чистые хелперы (Bezier, injectStrict) + тесты
```

У каждой директории **одна ответственность**. Межмодульное взаимодействие идёт через типизированные контракты в `types/`.

## 🎨 Технологический стек

| Слой          | Выбор                          | Почему                                        |
|---------------|--------------------------------|-----------------------------------------------|
| Фреймворк     | Vue 3 (Composition API)        | First-class TypeScript, гранулярная реактивность |
| Язык          | TypeScript (strict)            | Ловит ошибки на этапе компиляции              |
| UI-тулкит     | Vuetify 4                      | Зрелая темизация, design-токены, a11y из коробки |

**Чего намеренно нет**: lodash, Pinia, Axios, moment. Проект опирается на платформу и фреймворк, а не на зависимости.

## 🧭 Принципы проектирования

- **Markdown — источник истины** — UI это вид на текстовый документ, а не наоборот
- **Composition вместо inheritance** — каждая фича это composable-функция
- **Explicit вместо implicit** — типизированные injection-ключи, никаких magic strings
- **Single Responsibility** — один файл, одна ответственность
- **Тестировать то, что важно ломается** — чистая логика вместо поверхностных UI-тестов
- **Никакого vendor lock-in** — данные остаются в формате `.md`
